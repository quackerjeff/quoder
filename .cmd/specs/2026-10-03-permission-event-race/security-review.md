# Security Review: Permission Event Race

## Cycle 1 — 2026-10-03
Reviewing: Group 1 and Fix Group 1

### Threat Model
- **Trust boundaries.** The probe reads the v2 global SSE stream of its own child `opencode serve`. That server is authenticated with HTTP Basic using a per-run random password, so other local clients cannot subscribe or publish. Event *types* and IDs (`sessionID`, `id`) are generated by the server. Model output reaches the stream only as content inside server-generated events: question text, tool inputs, and permission asks that the model's own tool calls trigger.
- **New data flow.** Untrusted `permission.v2.asked` events are now recorded run-long, before the probe's own request exists, and they gate a `replyPermission(..., "once")`. A recorded `server.connected` frame gates the start of the run.
- **Attack surfaces.**
  - Model-triggered permission asks and questions in the probe's sessions.
  - Event fields `type`, `data.sessionID` and `data.id`.
  - The volume of events, which drives the sizes of `askedPermissions`, `waiters` and `pendingRejections`.
  - New journal markers.
- **Assets at risk.**
  - OpenCode's permission enforcement: the probe must grant only its own purpose-created `external_directory` request, and only once.
  - Sessions and requests of other clients.
  - The Basic credential and provider credentials, through the journal.
  - Process lifetime and memory.

- **Spoofed or out-of-scope events cannot redirect the reply.**
  - `replyPermission(sessionID, created.id, "once")` (line 867) takes its target only from the probe's own `first.id` and the server's `create` response, never from event data.
  - The recorded event only *gates* the reply. In the worst case, a forged or misattributed event would cause a `once` reply to the probe's own purpose-created request.
  - A model-triggered ask in the same session (for example from a tool call to an external path) is recorded, but its `id` never equals `created.id`, so it is never approved. It stays pending until settle or interrupt, as before.
- **Recorded before `create` returns.**
  - The waiter key embeds `created.id`, which is server-generated and unknown until `create` resolves.
  - An event recorded earlier can satisfy the wait only if it carries that exact ID in the same session. That means it is the server's own ask for this very request, which is the race the spec intends to cover.
  - There is no path to `once` without a recorded `(first.id, created.id)` match. On `timeout` or `monitor-ended`, the stage journals and returns without a reply (lines 864-866). Tests at 1612-1637 cover this for `none`, `otherSession`, `mismatchedId`, monitor ended early and monitor ended during the wait.
- **The key cannot collide (`sessionID \0 requestID`).**
  - Recording requires `sessionID ∈ #sessionIDs` (line 787), and those are server-issued session IDs.
  - For an event `(s', r')` to collide with the waiter `(s1, created.id)`, either `s' = s1` and `r' = created.id` (a genuine match), or one of the probe's own session IDs is a NUL-terminated prefix of the other. Server-issued IDs contain no NUL, so the second case cannot occur.
  - Even if a collision were possible, it would affect only the timing gate, never the reply target (see above).
- **Strictly one-time permission.**
  - The reply literal is `"once"`, and `createPermission` sends `save: []`.
  - `correlatePermissionEvidence` throws on any `effect` other than `"ask"` before waiting, so the stage journals `permission.failed.error` and sends no reply.
  - The probe sends no other permission reply, and it does not touch OpenCode's permission configuration.
- **`server.connected`.**
  - Only the authenticated child server emits frames; model content cannot set an event `type`.
  - The frame affects only *when* the run proceeds, and whether `event.monitor.unconfirmed` is journaled. A spoofed or early confirmation could at most reintroduce the race. That race yields Permission FAIL, never a false PASS, because acceptance still requires the exact correlated ID.
- **Resource bounds.**
  - `askedPermissions` grows only for asks in the probe's own sessions. Each model-triggered ask blocks its tool call until answered or interrupted, and the whole stream is bounded by `LIVE_PROBE_RUN_TIMEOUT_MS` and aborted in `stop()`.
  - At most one waiter exists (one permission stage). `finish` clears its timer and removes it on every path.
  - Each entry in `pendingRejections` is bounded by the adapter operation timeout, removed in `.finally`, and drained with `Promise.allSettled` on stop. Questions also block the model, which throttles how fast they arrive.
  - Neither a model nor a flood of events produces unbounded growth within a run's lifetime.
- **Journal safety.**
  - The new markers are fixed literals: `event.monitor.unconfirmed` and `event.monitor.ended`.
  - `permission.not-observed.${observation}` interpolates only the closed union `"timeout" | "monitor-ended"`; `"observed"` is excluded by the guard.
  - No event data, request IDs, error text or credentials are journaled.

### Variant Hunting
- **Other replies driven by events.** `rejectQuestion` is the only other action triggered by events. It uses the same scoping to own sessions (line 787) and a string `id` check, and it is a rejection, not a grant. This is unchanged in substance from the previously reviewed guard. Its rejections now run concurrently but are still tracked and awaited.
- **Acceptance without correlation.** I looked for any other path that sets `permissionRequestID` or calls `replyPermission`, and found none. The removed `#findPermissionEvent` and the per-stage subscription have no remaining references.
- **Comments versus code.** The doc comment at 751-760 and `docs/tech.md` (Permission Request section) match the implementation. Asks are recorded for own sessions only, the match is on the exact created ID, the reply is `once`, and an unconfirmed connection is journaled and the run continues.
- **Malformed `data`.** `Reflect.get(event.data, ...)` would throw on a frame with no data object. That would end the monitor, journal `event.monitor.ended`, and fail Permission. Only the trusted, authenticated child server can produce such a frame, and the outcome is fail-closed, so it is not a finding.
- **Unhandled rejection on a throwing journal write.** The general review's Cycle 2 noted the `rejection.finally` chain. It is a reliability concern with no attacker-controlled trigger (it needs a local I/O error), so it is not a security finding here.

### Verdict: PASS
